# DIST-001: Hori ARM64 RAM trial

## Result

On 2026-10-06 Asia/Manila, `aki@hori` (Raspberry Pi 5, AlmaLinux 10.2,
ARM64, Podman 5.8.2) completed the actual installer, CLI enrollment, resource
import, blueprint release, fleet assignment, agent, lifecycle, and systemd/Podman
path for one stateless Redis client. Both fleet and lifecycle listeners were
loopback-only; routing and OCI authorization were disabled for this trial.

The container recovered in **5.13 seconds** after `podman kill`. A **20-second**
control-plane outage, with an agent restart during the outage, left the same
client container running and healthy. On restoration, a fresh fleet observation
reported healthy with the same deployment ID, release digest, and assignment
generation. Client output included repeated RESP `PONG`.

## Proves

One AlmaLinux ARM64 host can enroll, consume the pinned blueprint release and
imported resource secret reference, recover its managed container, continue
locally while control-plane operations are unavailable, and publish fresh health
after reconnection. RAM path overrides work with the installed rootless services.

## Does not prove

The provider was a manually managed ephemeral Redis container on Hori, with
persistence disabled. Importing its resource identity does not demonstrate the
existing external Redis/Valkey provider required by the final owner procedure.
The second worker is unavailable because the other Pi lacks an SD card. No
AlmaLinux AMD64 execution, physical target-first movement, full owner procedure,
release-candidate package, or owner acceptance is claimed.

`DIST-001-HARDWARE` remains pending. The next physical attempt needs the
required second architecture/worker and external provider; retain the same
release identity and capture target-health-before-source-removal ordering.
